Positioning

Why agent skills over slash commands?

Slash commands are useful shortcuts, but they are a weak foundation for portable, evaluable agent capabilities. Skills can encode activation context, inputs, outputs, examples, and reusable behavior. That makes them much easier to inspect and compare.

Question

Does this measure the quality of a skill's outputs?

The hosted evaluator checks optional evals/evals.json declarations and local input paths. It does not execute uploaded tasks or assertions, compare baseline outputs, or measure output quality. Optional AI review assesses the skill's instructions and static summaries.

Missing fixtures are neutral. Invalid supplied fixtures produce advisory policy warnings. CSV input files can travel with local or GitHub skill packages. Public metadata contains validity and counts, without test prompts or input contents.

Actual evaluation needs separate clean runs with the skill and a baseline, output grading with concrete evidence, actual token and timing data, and human review. Uploaded benchmark or grading files remain supplied data. Follow the Agent Skills output evaluation guide.

Question

Why not just score Claude Code slash commands?

  • Commands are imperative one-shot triggers, not portable capability definitions.
  • They are usually coupled to one runtime's invocation model.
  • They rarely explain when they should trigger, what inputs they require, or what outputs they return.
  • That makes consistent evaluation much harder.
Question

Why evaluate the Agent Skills format across runtimes?

  • The evaluator checks the current Agent Skills specification and adds project quality policy.
  • Description optimization, script interfaces, security, MCP, token efficiency, and effectiveness checks are evaluator policy; policy failures do not necessarily mean invalid format.
  • The specification places no body-format restrictions. Under 500 lines is a recommendation; experimental allowed-tools strings and arbitrary string metadata are valid.
  • The goal is vendor-neutral reuse across Claude Code, Codex, Gemini CLI, Cursor, and similar environments.
Question

Why prefer .sh and .py helper scripts?

  • Evaluator portability policy prefers them when those runtimes are available.
  • The specification permits script languages supported by the runtime; other extensions produce portability warnings, not specification errors.
  • Document runtime requirements in compatibility. The legacy unsupported_script_types field is a policy signal.
Question

When does an evaluation leave traces and when does it not?

  • Deterministic-only runs do not send uploaded skill content to third-party AI providers.
  • The package is still processed locally for the duration of the run.
  • After the completed result is delivered to the browser, transient server-side progress and result state is released.
  • The final JSON remains available in the current browser tab for viewing and download, but it is not kept after refresh.
  • If optional AI review is enabled, uploaded skill content for that run is sent to the single provider selected for that run after deterministic evaluation.
Question

Is there a prebuilt Docker image?

  • Yes. A prebuilt application image is published as ghcr.io/sasa-fajkovic/agents-skill-eval-app:latest.
  • It bundles the Go backend, frontend assets, Redis, and deterministic evaluator into a single deployable container.
  • For local development, you can still build the image directly from docker/Dockerfile.app.
Question

Is the project open source and self-hostable?

Yes. The repository is public and the frontend ships as raw HTML, CSS, and JavaScript served by a Go backend. That keeps the deployment path simple and transparent.

Evaluation model

Why these checks exist.

Every check targets a concrete risk: wasted tokens from loose triggers, broken portability from vendor-locked helpers, or security gaps that surface only after a skill is already deployed across teams.

Customization

Tune scoring to match your team's standards.

All scoring parameters live in a single file inside the skill itself: scoring_config.json. Adjust deduction points, caps, tier boundaries, LLM tier base scores, and the weight split between deterministic and AI review scores. No server-side configuration or environment variables are needed — the skill is fully self-contained.

scoring_config.json
{ "penalties": { "error_penalty": 5, // points deducted per ERROR finding "error_cap": 70, // max total deduction from errors "warning_penalty": 2, // points deducted per WARNING finding "warning_cap": 30 // max total deduction from warnings }, "blending": { "deterministic_weight": 0.7, // weight of deterministic score in final blend "llm_weight": 0.3 // weight of AI review score in final blend }, "tiers": [ { "name": "excellent", "min_score": 90 }, { "name": "good", "min_score": 70 }, { "name": "needs_work", "min_score": 50 }, { "name": "poor", "min_score": 0 } ], "llm_tier_base_scores": { "excellent": 95, // LLM "excellent" maps to this score "good": 85, "needs_work": 60, "poor": 45 } }
  • Deterministic score starts at 100 and subtracts error_penalty per error (capped at error_cap) and warning_penalty per warning (capped at warning_cap).
  • AI review blend only applies when optional AI review is enabled. The final score is deterministic_weight × det_score + llm_weight × llm_score. Without AI review, the deterministic score is used directly.
  • Tiers are evaluated top-to-bottom; the first tier whose min_score the final score meets or exceeds becomes the quality tier.
  • LLM tier base scores convert the AI reviewer's qualitative tier label into a numeric score for blending.
  • Score caps override the penalty formula for critical structural issues. Missing frontmatter name (1.1) or description (1.2) caps the score at 75. Redirect/stub skills (4.8) cap the score at 35.

Does a good score prove that the description triggers correctly?

No. Description advice and trigger-query fixture checks are static. The evaluator does not install or invoke uploaded skills, so it cannot measure activation rates. Optional AI review also provides an assessment, not execution evidence.

Provide eval_queries.json, train_queries.json, or validation_queries.json in the skill root or evals/ to check their structure. Each contains an array of objects with a non-empty query string and a boolean should_trigger. Missing files are unpenalized. Malformed supplied fixtures produce an optional evaluator-policy warning under rule 4.9.

For empirical testing, install the skill in your target client and observe whether it loads for realistic positives and nearby requests it should exclude. Repeat runs, keep validation prompts held out, and check fresh prompts after revising. A useful negative trigger boundary is valid guidance. The description format limit is 1024 characters; a literal “Use when” clause is optional.
